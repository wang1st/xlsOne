## 二、严重漏洞详情

### 2.1 Ed25519 私钥种子 + ACTIVATION_SECRET 已入仓

**泄露位置**：

| 文件 | 行 | 泄露内容 |
|------|-----|---------|
| `docs/密钥落地-剩余步骤.md` | 18 | Ed25519 私钥种子 `9ae69c...` |
| `docs/密钥落地-剩余步骤.md` | 22 | ACTIVATION_SECRET `8c6b78...` |
| `activation/worker/wrangler.toml` | 23 | ACTIVATION_SECRET `8c6b78...` |

**首次入仓 commit**：`c00b558`（`docs/密钥落地-剩余步骤.md`）、`c9a697a`（`wrangler.toml`）

**影响**：
- 攻击者可用私钥种子签发任意设备的有效 Windows 授权文件（永久 / 年付不限），客户端 Ed25519 验签完全失效
- 攻击者可伪造 Mac 版 JWT Token，绕过 Mac 授权
- 攻击者可调用所有 Admin API（ADMIN_API_KEY 默认回退为 ACTIVATION_SECRET）

**注意**：`密钥落地-剩余步骤.md` 文件开头写的是"新种子/ACTIVATION_SECRET **仅存在于本次会话，未入库、未提交**"，但实际上已通过 `c00b558` 入库。

## 三、高危漏洞详情

### 3.1 Linux 授权完全绕过

**位置**：`cpp/core/src/license_manager.cpp:892-912`

- `loadOrCreateLinuxDefaultLicense()` 为所有 Linux 构建无条件授予 `PersonalLifetime` 许可证
- 不经过 Ed25519 签名验证，不连接服务端，不检查设备数
- 绕过方式：删除 QSettings 中 `license/linuxDefaultLifetime` 键即可重置

### 3.2 混淆保护薄弱

**位置**：`cpp/core/include/xlsone/core/obfuscation.hpp:17-19`

- `kObfKey` 是 `constexpr` 常量，出现在二进制 `.rodata` 段中，可被静态提取
- `decryptString` / `decryptByteArray` 是 `inline` 函数，XOR 解密逻辑简单
- 只能防止 `strings` 命令扫描，无法抵御 IDA/Ghidra 逆向
- 当前 `build-linux-release` 实际构建中 `XLSONE_OBFUSCATE=OFF`，完全未启用混淆

### 3.3 更新 URL 未混淆

**位置**：`cpp/app/src/main_window.cpp:618`

- `XLSONE_UPDATE_BASE_URL` 作为编译期字符串宏直接嵌入，不经过 `xlsone::obf::updateBaseUrl()`
- `obfuscated_secrets.cpp` 中的 `updateBaseUrl()` 已生成但无人调用
- 当 `XLSONE_OBFUSCATE=ON` 时，`XLSONE_UPDATE_BASE_URL` 不作为 compile definition 传入 → 依赖 CMake 变量默认值，且不是 C 预处理符号，可能导致编译失败

## 六、修复计划（按优先级）

### P0（立即执行，阻塞所有发布）

#### 6.1 轮换 Ed25519 密钥对

1. 生成新 Ed25519 密钥对（种子 + 公钥）
2. 部署新私钥种子到所有服务端：
   - 国内 Node 服务器 `47.97.115.235`：更新 `.env` 的 `ED25519_PRIVATE_KEY`，删除 `data/ed25519.pem`，重启服务
   - Cloudflare Worker：`wrangler secret put ED25519_PRIVATE_KEY --env production`（新值）
3. 轮换 ACTIVATION_SECRET：
   - 国内 Node 服务器：更新 `.env`
   - Cloudflare Worker：`wrangler secret put ACTIVATION_SECRET --env production`（新值）
   - **切勿再写入 `wrangler.toml`**
4. 更新客户端公钥：
   - `cpp/core/src/license_manager.cpp` 中 `kLicensePublicKey` 替换为新公钥
   - 设置环境变量 `XLSONE_LICENSE_PUBLIC_KEY=新公钥hex`，重编所有平台 Release 包
   - `cpp/core/src/obfuscated_secrets.cpp` 重新生成（`cmake --build` 会自动触发）
5. 部署新 ADMIN_API_KEY（不与 ACTIVATION_SECRET 相同，独立生成）
6. 验证：用新私钥签名 license → 用新公钥的客户端验证通过

#### 6.2 清理 Git 历史中的密钥

### P1（本轮发布前完成）

#### 6.3 Linux 授权加固

两个方案选择其一：

**方案 A（推荐）**：保留免费但加签名验证
- 生成一个专用的 Linux 内置 license，由服务端 Ed25519 签名，编译进客户端
- `loadOrCreateLinuxDefaultLicense()` 改为验证该签名后才授予
- 不再依赖 `QSettings` 标记

**方案 B**：改为编译期显式开关
- 将 `#if !defined(Q_OS_LINUX)` 改为 `#ifdef XLSONE_BUILD_LINUX_FREE`
- 仅内部构建启用，正式分发包不带此编译选项
- 正式分发走正常激活流程

#### 6.4 修复更新 URL 混淆

- `main_window.cpp:618` 的 `XLSONE_UPDATE_BASE_URL` 改为调用 `xlsone::obf::updateBaseUrl()`
- 在 `app/CMakeLists.txt` 中确保 obfuscated 构建也正确传入或生成 update URL
- 确保 `obfuscated_secrets.cpp` 中的 `updateBaseUrl()` 被实际调用

```cpp
// main_window.cpp checkForUpdates() 中
#if defined(XLSONE_OBFUSCATE)
    const QString apiUrl = xlsone::obf::updateBaseUrl() + XLSONE_OBF_STRING("/api/version");
#else
    const QString apiUrl = QStringLiteral(XLSONE_UPDATE_BASE_URL "/api/version");
#endif
```

#### 6.5 确保所有 Release 构建启用混淆

验证所有 release preset（`linux-release`、`windows-release`、`windows-cn-release`、`uos-*`）实际编译时 `XLSONE_OBFUSCATE=ON`，不是 CMakeCache 遗留的 OFF。

### P2（下一版本）

#### 6.6 服务端加固

1. **请求签名**：激活/试用接口加 nonce + timestamp + HMAC 签名，防重放
2. **Admin API 速率限制**：给管理接口也加速率限制
3. **独立 ADMIN_API_KEY**：不再默认回退为 ACTIVATION_SECRET
4. **Dev preset 改 HTTPS**：`CMakePresets.json` 中 dev preset 的 `XLSONE_UPDATE_BASE_URL` 改为 `https://z-pulse.cn`

#### 6.7 提升混淆强度

长期考虑引入真正的代码混淆工具（如 O-LLVM 控制流平坦化、虚假控制流、指令替换），或至少使用商业方案（VMProtect / Themida）。

当前混淆密钥结构保持编译期 XOR 不变，但可考虑：
- 将解密密钥分散存储（拆成多个变量、运行时拼接）
- 反调试检测（检测到调试器时不解密或自毁）

## 七、修复过程中注意事项

1. **顺序约束**：先部署服务端新密钥，再发布带新公钥的客户端。先部署国内 Node → 再部署 Worker → 最后发布客户端。
2. **已签发旧授权**：旧密钥签发的 license 文件在新客户端中判为无效。产品尚在早期，应无真实付费用户，影响可控。
3. **备份**：轮换前备份 `data/ed25519.pem` 和 `data/store.json`。
4. **验证路径**：每个部署步骤后做端到端测试（激活 → 验签 → 功能正常）。
